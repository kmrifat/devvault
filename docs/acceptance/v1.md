# v1 acceptance map

This file maps every acceptance criterion in `docs/PLAN.md`, and every
principle, to what proves it. It is the P4-09 checklist for v1. Update a row
in the same PR that changes its evidence.

Test names are written as `file › group › test`. Unless a path says otherwise,
it is under `test/`, or under the named package's `test/`.

## Status key

| Status | Meaning |
|---|---|
| **COVERED** | A test asserts the criterion, and CI runs it. |
| **COVERED (CI)** | A CI job is the evidence: builds, matrix runs or vectors. |
| **PARTIAL** | Part of the criterion is asserted. The note says which part isn't. |
| **MANUAL** | Needs a person, a device, a signed build or a paid account. See the [manual checklist](#manual-checklist). |
| **PENDING** | The work isn't on `main` yet. |

## Summary

- Nearly every criterion is COVERED by a test that CI runs on each PR. Goldens run on macOS and the rest on Linux. `core-matrix.yml` repeats the vault core on Linux, macOS and Windows.
- Nothing is **PENDING** on code. The store uploads and the device matrix in [p3.md](p3.md) are MANUAL.
- These are **MANUAL**: signed and notarized builds, the 14-day dogfood, the R2 run, real keyrings, and on-device behaviour (biometrics, app-switcher blur, a camera scan, a real 09:00 notification).
- The PARTIAL rows are listed under [known gaps](#known-gaps), each with the test that would close it.

The P4-09 PR added these tests, which closed four rows:

| `pairing_test › payload › the box holds the storage settings and keys, never a vault key` | PR-7 |
| `tool/network_boundary_test` | PR-5 |
