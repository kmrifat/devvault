# P2 gate: sync over S3

Gate (from `docs/PLAN.md` P2-14): an acceptance run against MinIO and R2
covering:
- the S3 request log for a password change;
- objects unreadable without the vault key;
- the AAD swap test (copy `items/a.enc` over `b.enc`);
- concurrent offline edits.

The run is `packages/vault_s3/test/acceptance_test.dart`, tagged
`acceptance`. It drives the real `SyncEngine` and `S3Backend` against
whatever bucket the `S3_TEST_*` variables name, under a fresh
`acceptance-<timestamp>/` folder. In CI it runs on every vault_s3 or sync
change against MinIO built from source (`.github/workflows/s3.yml`).
Without the variables it is skipped.

```bash
cd packages/vault_s3
S3_TEST_ENDPOINT=… S3_TEST_BUCKET=… S3_TEST_ACCESS_KEY=… S3_TEST_SECRET_KEY=… \
[S3_TEST_REGION=auto] dart test test/acceptance_test.dart -r expanded
```

## What each check does

1. **Password change is one write.** Device A syncs a vault, changes the
   master password and syncs again. The request log for that second sync
   must hold exactly one write: a `PUT` of `vault.json`.
2. **Unreadable without the key.**
   - Items with secrets and a `.p8`-looking attachment are synced.
   - Every object in the bucket is searched for the secret values, the
     titles, the PEM header and the file name: none may appear.
   - A vault with a different key must not be able to open any item.
3. **AAD swap.** With two devices in sync, item X's ciphertext is copied
   over item Y in the bucket. Device B's next sync must report one
   unreadable object and keep its own Y unchanged.
4. **Concurrent offline edits.**
   - Both devices change the same secret, and B also renames the item,
     then they sync A, B, A.
   - B's sync must record one conflict.
   - Both devices must end with identical items.
   - Both secret values must survive: one in the item, the other in its
     kept conflict version.
